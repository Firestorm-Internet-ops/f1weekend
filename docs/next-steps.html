Step 2 · Next

Show only activities near the race

The problem: race pages mix nearby activities with far-away day trips. Nothing checks distance. Activities are found by keyword search, some are tagged "day trip" on purpose, and the distance and travel-time fields are empty.

Branch: feature/nearby-activities-filter

Agreed rules ✓

GroupRuleWhen shown
Near circuit≤ 30 min (race-traffic adjusted)Between sessions
In the city≤ 60 minMornings and evenings; all day at night races
Day trips≤ 2 h, max 3 per raceThursday / Monday only, labelled
Everything else> 2 hHidden, with old pages redirected
  • Rules use travel time, not kilometres, with about 1.5× normal time for race-weekend traffic.
  • Night races (Singapore, Las Vegas, Bahrain, Saudi, Qatar, Abu Dhabi) show city activities all day.
  • Out-of-town circuits measure from where fans stay: Silverstone → Milton Keynes / Northampton, Spa → Liège, Suzuka → Nagoya, Zandvoort → Haarlem / Amsterdam, Red Bull Ring → Graz.

Progress

  • ✓ Distance rules written and tested (src/lib/nearby.ts, 10 tests with real places: Monaco, Silverstone, Monza, Suzuka).
  • ✓ Read-only audit script ready: npm run audit:nearby, which creates scripts/output/nearby-audit.html.
  • ✓ Audit page on staging: staging.f1weekend.co/api/nearby-audit. Review it before anything is hidden.
  • ✓ Experience map fixed. It was stuck on Melbourne for every race. It now centres on each race's circuit, with ~30 / ~60 min rings, pins coloured by distance, and markers for where fans stay (branch feature/experience-map-distance).
  • ✓ Free drawn map shown by default (map page + a preview on each experiences page). Google Maps loads only when someone clicks "Open interactive Google map", so most visits cost nothing. Clicks are tracked as map_open. Protection in Google Cloud: a 300/day quota on the Maps JavaScript API plus a $5 budget alert at 50 / 90 / 100%.

The plan

  1. Audit every race: how many activities are near, far or missing a location. This is read-only and changes nothing on the site.
  2. Fill in the distance and travel time for every activity.
  3. Apply the rules on the site: hide what's out of range, sort closest first, and show "15 min from circuit" on each card.
  4. Keep it clean: the data pipeline uses the same rules for new activities.

What you'll get

  • First: an audit report per race, which you review before anything is hidden.
  • Then: race pages with only nearby activities, each showing its travel time.
Now · Multi-provider pilot

Monaco: compare GetYourGuide, Viator and Tiqets

Branch: feature/multi-provider-experiences

Each experience keeps one page. Under it sit offers from every site that sells it, and fans pick the best price. Monaco is the first race.

Progress

  • ✓ Offers are separate from experiences: new experience_offers table; each click records which offer was used (affiliate_clicks.offer_id).
  • ✓ Booking links are built per provider (GetYourGuide, Viator, Tiqets). Copy on the pages says "Book on {provider}" instead of always "GetYourGuide".
  • ✓ Viator and Tiqets connected. First fetch for Monaco: 143 Viator and 33 Tiqets products.
  • ✓ Matcher: finds the same product on another site. Clear matches are attached automatically, look-alikes (different length, private vs shared) go to a review list. 15 tests.
  • ✓ Experience pages show a "Compare booking sites" block when there is more than one offer. With only GetYourGuide, pages look exactly as before.
  • ☐ Run the database migration, then the Monaco fetch with your experiences, and review the report.

How to run it

  1. npm run db:migrate-offers -- --dry-run, then without --dry-run. Adds the table and copies every current GetYourGuide link into it. Nothing is removed.
  2. npm run offers:fetch -- --race monaco-2026. Read-only. Opens scripts/output/offers-monaco-2026.html: automatic matches, matches that need your decision, and products not on the site yet.
  3. npm run offers:fetch -- --race monaco-2026 --apply --approve viator:CODE,tiqets:ID. Saves the automatic matches plus the ones you approved.

Safe for production data: the live site's code doesn't read the new table, so saved offers only appear once this branch reaches main.

How every change goes live

Preview first, then production

Only three branches at any time: main, staging, and one feature branch.

  1. Feature branch (now: feature/multi-provider-experiences). All coding happens here. It's fully tested, bottom up.
  2. Feature → staging. Merge it, then delete the feature branch. You check the change on the Vercel staging environment.
  3. staging → main, only after you confirm. That puts it live on f1weekend.co.

Things to know before step 2 goes live:

  • staging is 3 commits behind main. No extra step is needed: the feature branch starts from main, so merging it into staging brings those commits along.
  • Check which database previews use. Look in Vercel → Settings → Environment Variables → Preview. If previews use the production database, data changes would show on the live site immediately. So step 2 only adds distance data, and the hiding happens in code. The live site stays unchanged until the code reaches main.
