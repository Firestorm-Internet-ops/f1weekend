Going multi-provider: GetYourGuide + Viator + Tiqets + Headout

Plan to move f1weekend from a GetYourGuide-only listing to a comparison of offers from four providers, organised around F1 session times. Written 28 Sep 2026 from a review of the f1weekend repo.

Where to start, in one line: start the three partner applications today, because approval takes time. While they're pending, change the code so experiences and provider offers are separate things. Ship that with GYG as the only provider, so nothing on the site changes visibly. Then each new provider is a new adapter, not a rewrite.

1. The idea

Adding more listings isn't the goal on its own. The goal is for f1weekend to be the one F1 site that compares booking options and fits them around the race sessions. Each "thing to do" (e.g. Monaco helicopter ride) becomes a single page with one set of editorial content. Under it sit offers from every provider that sells it.

Coverage
Tiqets and Headout are strong on attraction tickets and skip-the-line entry, which suit short session gaps. Viator is strongest in the Americas (Miami, Austin, Vegas, Montreal, Mexico City).
Revenue resilience
Four affiliate programmes instead of one. We can send each click to the best offer: cheapest, best rated or highest commission.
SEO / AEO angle
Pages like "cheapest way to book X during the Monaco GP" are content that answer engines like to quote, and single-provider sites can't write them.

3. Target architecture

The provider interface

// src/lib/providers/types.ts
export type ProviderId = 'getyourguide' | 'viator' | 'tiqets' | 'headout';

export interface NormalizedOffer {
  provider: ProviderId;
  productId: string;
  title: string;
  url: string;              // clean product URL, no tracking params
  priceAmount: number | null;
  priceCurrency: string;
  rating: number | null;    // normalised to a 0–5 scale
  reviewCount: number;
  durationHours: number | null;
  lat: number | null;
  lng: number | null;
  flags: { instantConfirmation?: boolean; skipTheLine?: boolean; freeCancellation?: boolean; };
  raw: unknown;             // original payload, stored for re-processing
}

export interface Provider {
  id: ProviderId;
  displayName: string;      // "GetYourGuide", "Viator", ...
  search(q: { city: string; lat: number; lng: number; query?: string }): Promise<NormalizedOffer[]>;
  getDetail(productId: string): Promise<NormalizedOffer>;
  buildAffiliateUrl(url: string, ctx: { experienceId: number; source: string }): string;
}

Data model change

experience_offers
  id               int PK
  experience_id    int FK → experiences.id
  provider         varchar(20)     -- 'getyourguide' | 'viator' | 'tiqets' | 'headout'
  product_id       varchar(100)    -- UNIQUE(provider, product_id)
  url              varchar(1000)
  price_amount     decimal(10,2)
  price_currency   varchar(3)
  original_price   decimal(10,2)
  rating           decimal(3,1)
  review_count     int
  flags            json            -- instant confirmation, skip-the-line, free cancellation, ...
  options_snapshot json
  provider_categories json
  is_active        boolean
  last_synced_at   timestamp

affiliate_clicks  + offer_id int FK → experience_offers.id

Title, slug, editorial, F1 context, FAQs, windows and geodata stay on experiences. Anything provider-specific moves to offers. Denormalised "from" price and best rating are cached on experiences so list pages stay fast.

  • On list cards show "From €89 · 3 providers". On detail pages show an offer comparison block (price, rating, cancellation, instant confirmation).
  • Choose a default "best offer" rule: cheapest or best-rated by default, with commission as a tiebreaker.
  • Add per-provider click/conversion reporting from affiliate_clicks.
  • Add SEO/AEO content blocks such as "Cheapest way to book X for the {Race} GP", with FAQ schema.
5

Keep offers fresh

  • Run a scheduled job that re-syncs prices and availability per offer. Refresh more often close to race weekend.
  • Deactivate offers that disappear. If none are left, hide the experience or show "currently unavailable".
  • Revalidate affected pages through the existing /api/revalidate.

5. Deduplication: the hard part

The same Sagrada Família ticket or Monaco helicopter tour will appear on two to four platforms. If we list it several times the site looks spammy and near-duplicate pages compete with each other for SEO. Matching approach:

  1. Candidate filter: same race and city, within ~1 km of each other (when coordinates exist), similar duration.
  2. Score: title similarity (normalised tokens and landmark names) + distance + duration + category.
  3. Decide: high score → auto-attach as an offer. Middle → review queue (Claude can pre-judge "same product?"). Low → new experience.
  4. Canonical slug never changes when offers are added, so existing URLs and rankings are safe.

7. Risks

API access delays
Mitigation: phases 0–1 don't need any approval, and adapters can start from deeplinks or feeds.
Stale prices
Mitigation: last_synced_at, scheduled re-sync, and a "prices from, checked {date}" label.
Wrong matches
Mitigation: conservative thresholds, a review queue, and never merging offers from different venues.
SEO regressions
Mitigation: canonical slugs stay fixed, and we don't create a new page per provider.
Proposed first PR: Phase 1. It adds the experience_offers table, backfill migration, provider interface, GYG adapter, provider-aware /api/click and provider-neutral booking copy. The site should look exactly the same, and every later provider plugs in without touching the pages again.
